# 설계: 티어·분기 트리·부품 업그레이드·물리 모듈

작성 2026-10-15 · 기준 커밋 `9ed5e52`과 그 위의 미커밋 작업(10 대 10 매칭·구조 피해·AM 구조 보너스) · 상태: **설계 초안, 구현 전**

구현은 별도 작업자가 맡는다. 이 문서는 사용자와 정한 방향과 그 근거, 코드에서 먼저 손봐야 할 곳, 제안 작업 순서를 담는다. "결정"과 "제안"을 구분해서 읽는다. 제안 수치는 출발점일 뿐이며 균형 측정 전에는 확정하지 않는다.

## 0. 목표 한 줄

> 호위함 한 척으로 시작해서, 티어를 올리며 역할이 갈라지는 함선을 연구하고, 선체 안 실제 위치에 모듈을 꽂아 세팅하며, 내가 가진 함선으로 편대를 꾸려 출격한다.

---

## 1. 결정 사항 (사용자 확정)

1. **싱글 플레이 우선.** 진행 상황은 로컬에 저장한다. 다만 세팅을 함선 정의로 합치는 로직과 검증은 `src/Sim`에 두어 나중에 서버가 같은 코드를 돌릴 수 있게 한다.
2. **모듈은 물리화한다.** 장착 모듈은 선체 안의 실제 위치·크기·체력을 갖는다. 기존 피해 레이가 그대로 판정하고, 파괴되면 효과가 꺼진다.
3. **트리는 T1 호위함 하나에서 시작해** 티어가 오를수록 갈라진다.
4. **편대원 슬롯은 내가 보유한 함선으로 채운다.** 전함은 편대 안에 호위함 슬롯을 따로 둔다.
5. **미래 함급 두 개의 자리를 미리 잡아 둔다.** 드론모함(주포·미사일 없이 드론 여러 편대를 운용하는 항모)과 부유포대(주포에 극단적으로 투자하고 기동·방어가 약한 함)다.
6. **부유포대 주포는 함체 고정 축포**로 한다. 함 전체를 돌려서 조준한다.
7. 이번 작업은 **문서만** 만든다.

## 2. 네 축의 역할 구분

| 축 | 게임 안에서 맡는 일 | 성격 | 원칙 |
|---|---|---|---|
| 티어 | 전투력 단계, 매칭 기준 | 위로 성장 | 티어 차이는 체감되되 ±1 매칭에서 이길 수 있어야 한다 |
| 분기 트리 | 같은 함급 안의 역할 정체성 | 옆으로 갈라짐 | 분기끼리 상성이 있어야 한다 |
| 부품 업그레이드 | 연구로 그 함선을 완성 | 영구, 순수 상승 | **폭을 작게.** 미연구 상태가 고통스러우면 안 된다(스톡 노가다 회피) |
| 물리 모듈 | 판마다 고르는 개인 세팅 | 선택 | **모든 모듈에 대가가 있다.** "다 연구하면 정답 세팅 하나"가 되지 않게 |

## 3. 기술 트리

### 3.1 모양 (제안)

```
T1      T2          T3             T4               T5
호위함 ┬ 호위함Ⅱ ┬ 방공 호위함 ┬ 방공 호위함Ⅱ
       │         │             └ 드론 순양함 ──── 드론모함     ← 예약
       │         └ 포격 호위함 ┬ 전열 전함 ────── 전열 전함Ⅱ
       │                       └ 경포대 ───────── 부유포대     ← 예약
       └ 요격함 ┬ 정찰함 ──── 정찰함Ⅱ
                └ 강습함 ──── 강습함Ⅱ
```

- 5티어를 제안한다. 월오쉽식 10티어는 모델 제작 비용을 감당할 수 없다.
- 지구·화성은 **트리 모양은 같고 성격만 다르게** 가는 것을 제안한다(미확정). 지구는 장갑·근거리 화력, 화성은 장거리·정밀·전자전 쪽이다. 지금 수치도 이미 그 방향이다(구조 7200 대 5400, 프로브 30 km 대 36 km).
- 새 모델은 **두 티어마다 새 선체**를 만들고, 그 사이는 같은 모델의 개량형(포탑·방열판 외형만 교체)으로 처리하는 것을 제안한다. 처음에는 기존 모델에 수치·베이만 다른 변형으로 시작해도 된다.

### 3.2 기존 6종의 위치

| 기존 정의 | 트리 위치(기준점) |
|---|---|
| `escort`, `mars_escort` | T2 호위함Ⅱ |
| `interceptor`, `mars_interceptor` | T2 요격함 |
| `battleship`, `mars_battleship` | T4 전열 전함 |

T1 호위함은 지금 호위함의 축소판으로 제안한다. 포탑 1문에 베이도 적어서 모듈 개념을 처음 익히는 함이다. 새 모델을 만들지, 지금 호위함에서 포탑 하나를 뗀 변형으로 시작할지는 미결이다(§11).

### 3.3 분기별 성격 (제안)

| 함 | 강점 | 대가 | AI 교리 |
|---|---|---|---|
| 방공 호위함 | PD 4→6문과 명중률 상승, 대미사일 미사일(지금은 요격함 전용인 `canInterceptMissiles`를 확장) | 주포 1문, 미사일 탄수 감소 | 전함·아군 근접 엄호 |
| 포격 호위함 | 주포 장전·관통력 상승, 정면 장갑 | PD·디코이 감소 | 측면 기동 포격 |
| 정찰함 | 프로브 2→4기, 수명·센서 세기 상승, 신호 3→2 | AM 0~1발 | 외곽 정찰, 잠금 공유 |
| 강습함 | AM 2→3발, 구조 내구도·부스트 상승 | 프로브 없음 | 집결 후 동시 돌격 |
| 전열 전함 | 주포·장갑 특화 | 방어 드론 감소 | 대치 포격 |
| 드론 순양함 (T4) | 주포 일부 + 드론 1~2편대 | 화력·장갑 모두 중간 | 드론모함으로 넘어가는 과도기 |
| 경포대 (T4) | 부유포대의 약한 판 | 부유포대와 같음 | 부유포대와 같음 |

전자전 호위함(방해 세기 3→5, 디코이 강화, 신호 증가, 화력 약함)은 후보로 남겨 둔다.

### 3.4 상성 (설계 의도)

- 부유포대가 전함을 이긴다. 사거리가 더 길다.
- 드론모함이 부유포대를 이긴다. 드론이 PD가 약한 포대를 사냥한다.
- 방공 호위함과 전함이 드론모함을 이긴다. PD와 방어 드론이 드론을 막는다.
- 요격함은 근접에 약한 포대와 항모를 모두 위협한다.
- 정찰함과 저신호 세팅, 방공 호위함과 미사일 일제 사격, 전자전과 센서 특화도 서로 맞물린다.

Tab 명단에서 상대 편성이 보이므로, 출격 전에 상대 편성을 보고 대응하는 재미가 생긴다.

## 4. 티어와 매칭 (제안)

- 매칭 범위는 **±1 티어**, 티어 차이는 전투력 15~20% 정도다.
- 매칭 기준은 기함 티어가 아니라 **편대 전투력**이다(함마다 티어 점수를 합산). "T5 전함 + T5 호위함 2"와 "T5 전함 + T3 호위함 2"가 다르게 잡힌다.
- 팀 대칭은 지금 `Matchmaking.Create`가 함종·설계 수를 맞추는 방식이다. 이를 **체급 단위**로 바꾼다. 대형(전함·드론모함·부유포대), 중형(호위함 계열), 소형(요격함 계열)으로 나누면 새 함급이 추가돼도 대칭이 유지된다.
- 낮은 티어 판은 그 티어 ±1에 존재하는 함선으로만 AI를 편성한다. T1 판은 호위함만 나오는 입문 구간이 된다.

## 5. 편대 구성

### 5.1 규칙 (결정 + 제안)

| 편대 | 기함 | 편대원 슬롯 | 규칙 |
|---|---|---|---|
| 호위 전대 | 호위함 계열 | 3 | 같은 함급의 보유 함선, 기본값은 기함 복제 |
| 요격 편대 | 요격함 계열 | 4 | 같은 함급의 보유 함선, 기본값은 기함 복제 |
| 전투단 | 전함 | 호위 2 | 보유 호위함 중 선택, **티어는 기함 이하** |
| 항모 전단 (예약) | 드론모함 | 호위 2 | 전투단과 같은 규칙 |
| 포대 전단 (예약) | 부유포대 | 호위 2 또는 3 | 방어가 약하므로 3도 검토 |

- **보유는 수량이 아니라 해금이다.** 한 번 연구한 함은 몇 척이든 편대에 넣을 수 있다. 싱글 플레이에서 수량 경제는 재미보다 번거로움이 크다.
- 함선마다 **세팅 프리셋 2~3개**를 저장한다. 같은 호위함 4척을 "방공 세팅 2 + 포격 세팅 2"처럼 섞을 수 있다.
- 기함이 격침돼 편대원을 인계하면, 그 함은 **내가 맞춘 세팅 그대로**다. 편대원 세팅을 신경 쓸 이유가 생긴다.
- 전투단 호위 슬롯에 요격함을 허용하는 안(전함 + 요격 스크린)은 AI 교리가 더 필요하므로 보류한다.

## 6. 부품 업그레이드 (제안)

함선마다 연구 항목을 둔다. 각 항목은 기존 JSON 필드를 바꾸는 패치다.

| 항목 | 바뀌는 필드(예) |
|---|---|
| 선체 개량 | `structureHitPoints`, `shield.capacity`, 구획 `hitPoints` |
| 사격통제 | `railgun.reloadSeconds`, `sensorErrorMeters`, `sensorErrorPerKm`, 포탑 `yawRate` |
| 반응로 | `power.outputMw`, `power.coolingMw`, `power.heatCapacityMj` |
| 추진 | `flight.forwardAccel`, `pitchYawRateDeg` |
| 장갑 | 구획 `thicknessMm` (질량 증가와 함께) |
| 응급복구 | `damageControl.kits`, `repairSeconds` |

미연구 대비 완전 연구의 차이는 항목당 10~15% 이내로 제안한다. 매칭 전투력 점수에 연구 상태를 반영하면 스톡 함선이 일방적으로 불리해지는 것도 줄일 수 있다.

## 7. 물리 모듈

### 7.1 베이

함선 JSON에 `bays`를 추가한다. 지금 `modules`에 있는 주포·센서·반응로·탄약고 같은 **핵심 모듈은 고정**이고, 베이는 **교체 가능한 슬롯**이다.

```json
"bays": [
  { "id": "bay-fore-1", "size": "Medium", "center": [0, 0, -100], "halfSize": [10, 8, 14],
    "grid": "Shared", "accepts": ["Shield", "Sensor", "Ecm"] },
  { "id": "bay-mid-1", "size": "Large", "center": [0, -6, 20], "halfSize": [14, 10, 22],
    "grid": "Port", "accepts": ["Drone", "Defense", "Survival"] }
]
```

- 크기는 소·중·대·**특대**다. 특대는 드론모함 격납고와 부유포대 축포처럼 함 길이 방향으로 긴 공간을 위해 지금 예약해 둔다.
- 베이 위치는 디자이너가 정한다. 같은 모듈이라도 함수 베이에 꽂으면 정면 피탄에, 함미 베이에 꽂으면 추격전에 먼저 부서진다. **세팅이 곧 취약점 지도**가 된다.
- 기존 검증 규칙(모듈은 선체 구획 안에 있어야 함)을 베이에도 적용한다.

### 7.2 모듈 데이터

모듈은 `data/modules/*.json`에 따로 둔다.

```json
{ "id": "ecm-amp-1", "name": "ECM 증폭기", "category": "Ecm", "size": "Medium",
  "kind": "EcmSuite", "hitPoints": 60, "resistanceMm": 20,
  "powerMw": 30, "heatMw": 8, "massKg": 400000,
  "criticalChance": 0, "effects": { "sensors.jammer": "+1.5" } }
```

### 7.3 장착 규칙

1. 베이 크기와 허용 분류가 맞아야 한다.
2. **전력 예산.** 기존 `Validate`가 "균형 배분 합(`engines+shields+weapons+sensors`)이 `outputMw`를 넘으면 안 된다"를 이미 검사한다. 모듈의 `powerMw`를 해당 채널 사용량에 더한 뒤 같은 검사를 통과해야 한다.
3. **열.** 모듈 `heatMw`는 `coolingMw` 여유를 줄인다.
4. **질량.** 질량 합이 늘면 가속을 보정한다. 지금 `flight`에는 가속이 직접 적혀 있으므로 `기본 가속 × 기본 질량 ÷ 장착 후 질량`으로 줄이는 방식을 제안한다.

### 7.4 피해와 효과

- 장착하면 베이 위치·크기로 `ModuleDefinition`을 생성해 `Modules`에 넣는다. **피해 레이(`DamageRay`)와 구조 피해는 수정 없이 그대로 동작해야 한다.**
- 새 효과를 위해 `ModuleKind`를 늘린다(예: `EcmSuite`, `DroneBay`, `LaunchBay`, `DataLink`, `ShieldBooster`). 모듈이 파괴되면 해당 효과가 꺼져야 하므로, 효과를 정의값에 합쳐 버리지 말고 **"모듈이 살아 있을 때만 적용"**되게 `Subsystems`·센서·실드 쪽에 연결한다. 이 부분이 작업량이 가장 크다.
- 드론 격납고·추가 탄약고처럼 위험한 모듈은 `criticalChance`를 갖는다. 지금 검증은 `criticalChance`를 `Magazine`·`Reactor`에만 허용하므로 그 조건을 넓혀야 한다. 유폭 처리는 기존 핵심부 유폭 규칙에 얹는다.

### 7.5 초기 모듈 후보 (제안, 모두 대가가 있음)

| 분류 | 모듈 | 장점 | 대가 |
|---|---|---|---|
| 실드 | 고용량 발생기 | `shield.capacity` +40% | `rechargeDelay` 증가, 전력 증가 |
| 실드 | 급속 재충전기 | `rechargePerSecond` 상승 | 용량 감소 |
| 드론 | 드론 격납고 확장 | 방어 드론 수 증가 | 대형 베이, 피격 시 유폭 위험 |
| 드론 | 요격 드론 펌웨어 | 드론의 미사일 요격 강화 | 대함 대응 감소 |
| 탐지 | 고출력 센서 | `sensors.strength` 상승 | `signature` 증가 |
| 탐지 | 저신호 도장 | `signature` 감소 | 냉각 감소 |
| 탐지 | 데이터 링크 중계기 | 아군 공유 잠금 품질 상승 | 전력 |
| 방해 | ECM 증폭기 | `jammer` +1~2 | 열 |
| 방해 | 디코이 발사기 | 디코이 수·신호 배율 상승 | 소형 베이 차지 |
| 생존 | 탄약고 방호 | 탄약고 유폭 확률 감소 | 탄수 감소 |
| 생존 | 응급복구 키트 | 키트 +2 | 질량 |

1차 구현은 고용량 실드, ECM 증폭기, 고출력 센서, 드론 격납고 확장의 4종이면 충분하다.

### 7.6 격납고 화면

- 함선 단면(또는 투명 선체) 위에 베이를 표시하고, 모듈을 꽂으면 전력·열·가속 막대가 바로 바뀐다.
- 사용자는 HUD에서 글자보다 도형·게이지를 선호한다. 메뉴 화면이라 제목·버튼 글자는 괜찮지만, 수치 비교는 막대로 보여 준다.
- 함선 모델 표시는 `src/Game/ModelGallery.cs`를 참고한다.

## 8. 예약 함급

지금 구현하지 않는다. 다만 §9의 구조 작업에서 이 두 함급이 들어올 자리를 막지 않아야 한다.

### 8.1 드론모함

- **무장**: 주포·미사일 없음. PD와 방어 드론만 있다. 정의상 `Railgun`·`Missiles`는 이미 선택 필드다(§9.3 참고).
- **드론 편대는 기존 `DefenseDrones`와 별도 시스템**이다. 방어 드론은 모함에 묶여 근처를 도는 방어용이라 구조가 다르다. 새 정의(가칭 `DroneWingDefinition`)를 둔다.

  | 드론 편대 | 역할 |
  |---|---|
  | 공격 드론 | 낮은 관통력으로 여러 번 때려 겉 모듈(방열판·센서·PD)을 노림 |
  | 요격 드론 | 대미사일·대요격함 초계 |
  | 정찰 드론 | 이동하는 센서 노드, 데이터 링크 확장 |
  | 전자전 드론 | 전방 재밍 |

- **물리 모듈 연결**: 격납고(`DroneBay`)와 사출구(`LaunchBay`)를 특대·대형 베이 모듈로 둔다. 사출구가 부서지면 발진이 멈추고, 격납고는 유폭 위험이 있다.
- **재무장**: 드론은 모함으로 돌아와야 재무장한다. 잃은 드론은 보충 한도 안에서만 채운다.
- **통제 링크**: 모함에서 멀어지거나 적 ECM을 받으면 자율 모드로 떨어져 효율이 낮아진다.
- **성능 예산**: 240Hz 시뮬레이션에 함선이 80척 안팎이다. 모함당 드론 상한(예: 4편대 × 6기)을 처음부터 정하고, 작은 표적은 기존 `SmallContactSensors`·`SmallTargetCombat` 경로를 쓴다.
- **지휘 방식은 미결**(§11). 편대별로 직접 명령(기존 `SquadCommands`와 전체 지도 재사용)하는 방식과, 교리만 정하고 AI가 운용하는 방식이 있다.

### 8.2 부유포대 (고정 축포)

- **주포**: 함체에 고정된 축포 1문이다. 포각은 정면 몇 도 이내로 아주 좁고, **함 전체를 돌려서 조준**한다. 사거리·관통력·사격통제 정밀도를 극단적으로 높인다.
- **약점**: 가속·선회가 낮다. 장갑·실드가 얇고 PD가 적다. 발사할 때 열과 신호가 크게 튀어서 위치가 드러난다.
- **데이터 표현**: 기존 `railgun.traverseDegrees`와 포탑 `yawDegrees`를 아주 작게 주는 것으로 표현할 수 있는지 먼저 검토한다. 축포는 특대 베이 또는 고정 핵심 모듈로 둔다.
- **조작**: 기존 망원 조준(`TelescopeHud`)과 함 회전 입력을 조합한다. 포각 밖 표적은 "함을 돌려야 함"을 도형으로 보여 준다. 기존 사격 방위구 표시를 확장한다.
- **AI**: 소행성 지형의 사격 위치 탐색(`TerrainFiringPosition`)으로 자리를 잡고, 함 전체 회전으로 조준한다.
- **정찰 의존**: 아군 공유 잠금으로 주포를 쏠 수 있는 기능이 이미 있다. **정찰함이 잠그고 포대가 쏘는** 조합이 바로 성립한다.
- **후보 메커니즘**(채택 미결): 충전 사격(무장 핍을 몰아 충전, 발사 시 큰 `shotHeatMj`), 거치 모드(거치하면 정확도·사거리 상승, 기동 거의 불가, 해제에 시간 소요).

## 9. 코드 구조 영향 (구현자 필독)

### 9.1 Loadout 합성 층

- `ShipDefinition`은 JSON에서 읽는 불변 객체이고, `Parse` 안에서 `Validate`를 거친 뒤 충돌 선체와 실드 외피를 만든다.
- 제안: **기본 JSON → 분기 패치 → 업그레이드 패치 → 모듈 장착 → `ShipDefinition.Parse`**. JSON 단계에서 합치면 기존 검증·선체·실드 계산을 그대로 탈 수 있다.
- 위치는 `src/Sim`이다. Godot 노드 의존을 넣지 않는다.
- 합성 결과에는 `LoadoutId`와 내용 해시를 붙여 재현과 기록에 쓴다.
- **필수 검사: 빈 세팅으로 합성한 정의는 기존 정의와 같아야 한다.** 그래야 기존 SimChecks 결과가 그대로 유지된다. 기본 세팅이 전투 결과를 바꾸면 그것은 "결과 변경"이므로 사용자 허용을 먼저 받는다(경로 탐색 분할 때와 같은 원칙).

### 9.2 `HullKind` 분기

- `HullKind`(Battleship·Escort·Interceptor)는 `src`·`tests`·`tools`의 62개 파일에서 쓰이고, `src`에만 `switch`·비교 분기가 100곳 가까이 있다(2026-10-15 기준).
- 상당수가 `_ =>` 기본값으로 끝난다. 새 값을 그냥 추가하면 **컴파일은 되는데 조용히 요격함 취급**을 받는다. 예:
  - `src/Sim/Matchmaking.cs:17` `ShipCount` (`_ => 5`), `:18` `Role`, `:20` `Composition`
  - `src/Sim/SimAI.cs:716` 표적 선호
  - `src/Sim/ShipAI.cs:58` 기본 핍
  - `src/Sim/BattleRules.cs:50` 전력 점수
  - `src/Game/SquadronHud.cs:37`, `src/Game/CombatAudio.cs:148`·`:219`, `src/Game/FleetAudio.cs:197`, `src/View/BattleFx.cs:199`
- 제안:
  1. 편대 크기·슬롯 규칙·AI 역할·매칭 체급·표시 크기 같은 **함급별 상수를 데이터로** 옮긴다(함선 JSON의 `squadron` 블록 등).
  2. 새 코드에서는 `HullKind` 분기를 늘리지 않는다.
  3. 분기 정체성(방공·포격 등)은 `HullKind`가 아니라 별도 필드(가칭 `Branch`)로 둔다. `HullKind`는 기본 물리·행동 체급으로 남긴다.
  4. 새 함급을 추가하는 작업에서는 `_ =>` 기본값 분기를 전수 점검한다.

### 9.3 주포 없는 함선

- `Railgun`은 정의상 선택 필드이지만, 실행 코드에 `Railgun!` 가정이 남아 있다: `src/Game/GunneryHud.cs:97`·`:98`·`:155`, `src/Game/TelescopeHud.cs:51`, `src/Sim/InterceptorMissions.cs:237`·`:239`. 검사 코드에도 여러 곳 있다.
- 드론모함 전에 **주포·미사일이 없는 시험 함선으로 AI·HUD·사격 패널을 한 판 돌리는 검사**를 넣는다.

### 9.4 편대 역할

- `SquadronRole`(`src/Sim/Squadron.cs:7`)은 BattleGroup·EscortSquadron·InterceptorWing 3개이고 함종에 묶여 있다.
- 분기마다 행동이 달라야 의미가 있다. 방공 호위함이 포격 호위함처럼 측면 돌격하면 분기 의미가 없다. 역할을 분기 단위로 넓히고 `FleetDoctrine`·`MarsDoctrine`에 연결한다.

### 9.5 매칭과 저장

- `MatchParticipant`는 지금 `HullId`만 갖는다(`src/Sim/Matchmaking.cs:9`). 편대 단위 세팅(기함 + 편대원 각각의 `LoadoutId`)을 갖도록 바꾸고, AI 참가자는 티어별 프리셋 세팅을 쓴다.
- 함선 선택은 지금 `user://fleet-choice.cfg`에 저장된다(`src/Game/MatchFlow.cs:21`·`:31`). 진행 상황(해금·연구·세팅·편대)은 `user://progress.cfg` 같은 별도 파일에 두고, 기존 선택 파일을 마이그레이션한다.
- 진행·저장·UI는 `src/Game`, 합성·검증·매칭은 `src/Sim`에 둔다.

### 9.6 성능

- 물리 모듈은 함당 모듈 수를 늘려 피해 레이 비용을 키운다. 드론모함은 소형 물체 수를 크게 늘린다.
- 기존 측정 도구(`--perf-trace`, `docs/BALANCE_perf.md`의 방법)로 변경 전후를 비교한다.

## 10. 작업 단계 (제안 순서)

순서는 **구조 → 모듈 → 분기 → 편대·UI → 진행 → 예약 함급**이다. 앞 단계 없이 뒤 단계를 하면 `HullKind` 분기와 정의 합성을 두 번 고치게 된다.

| 단계 | 내용 | 완료 기준 |
|---|---|---|
| 1 | Loadout 합성 층 + 함급 상수 데이터화(§9.1, §9.2) | 빈 세팅 동일성 검사 통과, 기존 SimChecks 수치 불변, `Matchmaking`의 함종 `switch` 제거 |
| 2 | 베이 + 물리 모듈 4종(§7) | 장착 모듈이 피해 레이에 맞고, 파괴 시 효과가 꺼지는 검사. 전력·크기 초과 세팅 거부 검사 |
| 3 | 호위함 분기 2종(방공·포격) + AI 역할 분리(§3.3, §9.4) | `tools/BattleBatch`로 역할 차이 측정(예: 방공 호위함의 미사일 요격 수, 포격 호위함의 주포 명중). 소표본 승률로 균형을 주장하지 않는다 |
| 4 | 편대 슬롯·프리셋·격납고 화면(§5, §7.6) | 편대원 세팅이 출격·인계 후에도 유지됨. 화면 렌더 확인 |
| 5 | 티어·연구·진행 저장·티어 매칭·T1 호위함(§4, §6) | 저장/불러오기 왕복, ±1 매칭 대칭 검사, 기존 선택 파일 마이그레이션 |
| 6 | 예약 함급: 부유포대 먼저, 그다음 드론모함(§8) | 주포 없는 함 검사(§9.3), 드론 수 상한에서 성능 측정 |

부유포대를 먼저 제안하는 이유: 주포·센서 공유·지형 사격 위치 등 기존 시스템을 많이 재사용하고, 드론모함은 새 드론 편대 시스템이 필요해서 작업이 훨씬 크다.

## 11. 미결 사항

- 드론모함 지휘 방식: 편대별 직접 명령 대 교리 + AI 운용.
- T1 호위함: 새 모델 대 기존 호위함에서 포탑 1문을 뗀 변형.
- 지구·화성 트리 모양 공통 여부(제안: 공통, 성격만 다름).
- 부유포대 충전 사격·거치 모드 채택 여부.
- 티어 수(제안 5)와 티어당 전투력 폭(제안 15~20%).
- 전자전 호위함 분기 추가 여부.
- 전투단 호위 슬롯에 요격함 허용 여부.
