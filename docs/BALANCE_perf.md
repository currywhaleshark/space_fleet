# 시뮬레이션 성능 — 기준값과 결과 보존 최적화

2026-10-10 · [작업지시서](WORKORDER_sim_performance.md) 1차 측정 및 2차 최적화

## 범위와 기준

이 절부터 재현 명령까지는 구간 측정기와 결과 비교 도구를 넣은 **1차 작업 기록**이다. 당시에는 알고리즘 최적화, AI·무장 수치 변경, 물리 틱·배속 제한을 적용하지 않았다. Release 평균 0.2 ms / 난전 p99 0.6 ms 및 Debug ×4의 10분 순간 30 FPS 목표에 대한 **2차 결과는 문서 마지막**에서 구분한다.

원본은 `d5824a2760a51b6e8528906e0d1dc22c82526fa3`. 코드를 수정하기 전에 이 커밋의 배치 실행본을 보존하고 시드 1~10 × 원본/미러 20판을 실행했다. 원본 전투 요약과 함선·AM 비행 기록, 계측 결과는 [원자료 디렉터리](balance/perf_stage1_20261010/)에 보관한다. 커밋 이전 실행본과 새 계측 실행본은 구분한다.

성능 측정은 `jobs=1`로 한 판씩 실행했다. 전투 결과 비교만 `jobs=6`으로 실행했다. 동시에 다른 검사를 돌리지 않았지만 OS·사용자 프로그램의 부하, CPU 클럭, JIT·GC는 통제하지 않았다. 첫 틱의 초기화 비용도 포함하므로 최대값과 단일 실행 간 차이를 최적화 효과로 해석하면 안 된다.

## 계측 구현

- `src/Sim/SimProfiler.cs`: Stopwatch 기반 스레드별 카운터. 측정 호출 자체에는 켜짐/꺼짐 모두 할당이 없다. 스냅샷을 출력할 때만 자료구조를 만든다. 병렬 배치는 각 작업자 안에서 활성화·초기화·정리한다.
- `SimWorld`, `SimAI`, `SimMissiles`: 기존 실행 순서를 유지하며 AI·사격통제·함선·충돌·탄도·미사일·PD·드론·센서·마무리를 측정한다. `Tick`은 전체 틱, `AI`는 네 하위 구간을 포함한다.
- `BattleBatch --profile`: 30초 전투 기록 경계와 판정 직전 마지막 부분 구간을 저장한다. `.sections.csv`에 실제 전투 국면 및 시간대별 호출 수·총 ms·µs/틱을 기록한다. `--tick-profile`은 바깥 틱만 측정한다.
- 모든 배치는 `.summaries.json`을 저장한다. `--compare-summaries`는 시드/미러 집합과 요약 문자열을 정확히 비교하며 누락·중복·내용 차이가 있으면 실패한다.
- 게임 `--perf-trace`: 기존 프레임 정보에 같은 구간의 `sim-profile` 행을 추가한다. 첫 화면 프레임에서 카운터를 비워 `--advance` 준비 구간을 제외한다. `--perf-no-sim-profile`은 프레임 측정만 유지한다.
- `tools/analyze-sim-profile.py`: 국면·시간대 합계, 틱/하위 틱 호출 수, 중복 행, 단위 변환과 포함 구간의 중복 집계를 검사한다.

## Release 20판 — 알고리즘 변경 전

`profile-release.csv`와 `.sections.csv`, 총 **929,367틱**. 아래는 판별 평균의 단순 평균이 아니라 **총 측정 시간 ÷ 총 틱 수**다. 단위는 **60 Hz 틱당 µs**이며, 함선·충돌·탄도·미사일·PD·드론은 240 Hz 하위 틱 4회의 합이다.

`Tick`과 `AI`는 포함 구간이므로 자식 구간과 함께 더하지 않는다. 측정 호출 사이의 비용은 부모에만 잡힌다. 하위 틱 6개 구간 각각의 호출 수가 `틱 수 × 4`이고, 국면별/시간대별 합계가 전체와 일치함을 검증했다.

바깥 `World.Step` Stopwatch 평균은 **0.3929 ms**, 내부 `Tick` 평균은 **0.3927 ms**다. 판별 평균의 범위는 0.312~0.483 ms(중앙값 0.379). 전체 p99는 **각 판별** 0.911~1.897 ms(중앙값 1.1395), 난전이 존재한 17판의 **각 판별 난전 p99**는 0.795~2.445 ms(중앙값 1.409)다. 이 값들은 20판의 모든 틱을 합친 p99가 아니다.

실제 `Brawl` 국면 평균은 0.4760 ms이며, 레일건 탄 160.10 µs가 가장 크다. 실제 `Missile` 국면에서는 근접방어 121.50 µs가 가장 크다. 먼저 PD 후보 검색을 줄이고 이후 포탄의 후보 함선/드론 검사를 줄이는 순서가 타당하다. 충돌·함선 갱신은 Debug에서 특히 비싸므로 함께 관찰한다.

## 게임 FPS

실제 렌더러의 Debug 및 새 ExportRelease 실행본에서 시드 1, 자동 관전 ×4, `--perf-trace`를 사용했다. ### 관전 중 발견한 별도 문제

ExportRelease 약 668~672초 사이에 `Hud.DrawSquadOrders`의 `DrawColoredPolygon`에서 `Invalid polygon data, triangulation failed` 오류가 **1회** 기록됐다. 게임은 판정·결과 화면까지 진행하고 종료 코드 0으로 끝났다. 이 로그도 삭제하지 않고 보존했다. 화면 코드는 이번 시뮬레이션 계측 범위에서 수정하지 않았으며, 도형 퇴화 조건에 대한 후속 확인이 필요하다. Debug 관전에는 해당 오류가 없었다. 따라서 이번 Release FPS는 이 비치명 오류가 포함된 단일 실행의 관측값이다.

## 2차 — 결과를 보존하는 최적화

### 변경과 경계 조건

1. **PD 후보 검색 (`SimMissiles`, `PointDefense`)**: 실제 포대 위치 전체를 둘러싼 범위를 함선 단위로 계산하고 미사일·요격함·드론 모함 후보를 먼저 추린다. 후보 순서와 동률 처리, 표적 종류별 우선순위는 보존한다. 다른 포대가 후보를 파괴하면 다음 포대에서 생존 여부를 다시 확인한다. 이전 표적보다 우선하지 못하는 드론에는 가림 광선을 쏘지 않는다. 같은 자세의 역회전과 변하지 않는 포대 각도 상수를 재사용한다.
2. **포탄·드론 (`SimBallistics`, `DroneCombat`)**: 매 240 Hz 하위 틱에서 함선과 실제 드론 위치의 이동 범위를 만들고, 포탄의 이동 범위와 겹칠 수 있는 경우에만 기존 상대 이동·구체/상자 교차를 계산한다. 수명 끝의 짧은 이동도 포함한다. 실드 소진·같은 하위 틱의 격침으로 바뀔 수 있는 함체 반경과 드론 생존 여부는 후보 검사 시점에 다시 읽는다.
3. **충돌 (`ShipCollision`)**: 넉넉한 이동 범위로 먼 쌍을 먼저 제외한다. 충돌 보정 직후 두 함선의 범위를 다시 계산하므로, 보정에 밀려 제3의 함선과 닿거나 새 잔해가 생기는 경우도 기존 순서로 검사한다. 범위 밖 후보를 고정한 채 여러 보정 패스에서 재사용하지 않는다. 기존 SAT·연속 판정·8회 겹침 보정은 유지한다.
4. **반복 상태 조회 (`ShipDamage`, `Railgun`, `DefenseDrones`)**: 모듈의 불변 종류별 목록에 살아 있는 `ModuleState` 참조를 보관해 전체 모듈을 반복 탐색하지 않는다. 평균의 합산 순서와 직접 체력 수정/수리 반영은 유지한다. 같은 주포 하위 틱의 출력 조회는 한 번만 하고, 드론 생존 수의 LINQ 열거를 단순 순회로 바꾼다.
5. **불필요한 관통 예측 (`Gunnery`)**: 장갑 광선 예측을 사거리·사계·정렬·장전 검사 뒤로 옮겼다. 순수 조회만 건너뛰며 `gun.Aim()`의 호출 시점·값, 포탑 추적 앞당김, 표시되는 실패 상태의 우선순위와 실제 발사 조건은 유지한다.

`SpatialBounds`는 double 좌표의 보수적 후보 검사다. 1 m 및 좌표 크기에 따른 수치 여유를 두고, 통과한 후보는 원래 정밀 판정으로 결정한다. 원점, 1e9, -1e12, 1e16 위치에서 이동 양 끝·중간과 반경 경계, 교차/비교차 경로를 5,608회 검사했다. 검사를 줄인 것은 **명백히 닿을 수 없는 후보**이며 물리 주기나 충돌 정밀도를 낮추지 않았다.

### Debug 게임과 배치의 추가 차이 조사

GPU 경합으로 단정했던 이전 가설 대신 실행 조건을 대조했다. 실행 중인 Godot 프로세스의 모듈 경로/해시를 읽어 개발 게임이 설치 폴더의 `GodotSharp/Api/Debug/GodotSharp.dll`을 로드함을 확인했다. 반면 배치의 참조 경로는 `.godot/mono/temp/bin/Debug`라는 이름이지만, 그 안의 `GodotSharp.dll`은 설치된 **Release API와 같은 파일**이었다. 경로 이름만으로 수학 라이브러리의 구성을 판단하면 안 된다.

- 게임에서 실제 로드한 Debug API SHA-256: `af104a6fdca648c2092b542ce49a773ee4c3a1388d065968bb42a80ace49e84e`
- 기존 배치 및 Release API SHA-256: `2afe2686aacfefac36da6601b59aeb05e560f06e4970cd5036100acd2ca4249d`

**남은 차이:** Debug 게임의 전투 상태가 기준 배치와 달라지는 근본 원인은 미해결이다. 수학 라이브러리 교체는 배치의 결과를 바꾸지 않았고 GPU 제거도 게임 결과를 바꾸지 않았다. 설정/초기화 및 화면 루프와 시뮬레이션 상태의 상호작용을 더 세분화해야 하며, 이를 맞추기 위한 행동·판정 변경은 이번에 하지 않았다. 수학 라이브러리 차이 때문에 승패가 바뀐다고 결론내리지 않는다.

ExportRelease 게임은 기준 배치와 판정 시각·승자·첫 사건 시각이 같다. 새 `autoplay summary`는 판정 틱 직후가 아니라 다음 화면 프레임에서 기록하므로, 735.217초 판정 뒤 735.267초 스냅샷까지 추가된 명중/이벤트가 포함될 수 있다(배치 이벤트 123, 게임 126). 이 스냅샷 요약을 배치의 틱 단위 정확 비교 대신 사용하지 않았다. 이번 결과 불변 판정은 변경 단계별 및 최종 20판 배치의 정확한 요약과 최종 상태 파일을 근거로 한다.

### 범위와 구현

기준은 점령전이 추가된 `824d91a`다. 2차 당시와 함선·무장·AI 구성이 달라졌으므로 옛 0.169ms 기록을 이번 변경의 직접 기준으로 사용하지 않았다. 수정 전 배치 실행파일과 소스·Debug 어셈블리를 보존하고 같은 데이터로 비교했다. **잔해의 충돌 수명·개수·형상·이동과 240Hz 연속 충돌, 접촉/피해 적용 순서를 유지했다.** 결과 변경 방식은 적용하지 않았다.

- `WreckLayout.cs`, `CollisionHull.cs`, `ShipBody.cs`: 함선마다 잔해 충돌체와 상자 배열을 한 번 만들고 각 하위 틱의 회전·드리프트·경계만 갱신한다. 파괴 유형/리셋 버전이 바뀌면 새 배열을 만들며 수리하면 원래 함체로 돌아간다. `ShipBody.Hull`은 갱신되는 현재 충돌체이고, 별도 시점의 보관용 `Wreck.Hull(age)`는 독립 스냅샷을 계속 반환한다.
- `CollisionHull.cs`, `ShipCollision.cs`: 잔해의 2~8개 조각별 상자 범위를 유지한다. 각 조각을 포함하는 이동 경계가 겹치지 않으면 해당 상자 묶음을 제외한다. double 절대 좌표의 기존 여유값과 조각의 float 변환 오차 여유를 더한다. 좁은 단계와 동일하게 현재 조각 자세를 이동 양 끝에 사용하며, 기존 회전 근사를 바꾸지 않았다.
- `ShipCollision.cs`: 동일한 호출에서 상자별 중심과 15개 축 투영 반경을 한 번 계산한다. 겹침 검사에서 한 축이라도 분리가 확인되면 나머지 축은 계산하지 않는다. 연속 접촉은 기존 진입/이탈 시간 검사를 유지한다. 원래 상자 A → 상자 B 순서와 동시 접촉 우선순위, 접촉 후 경계 재계산을 보존했다.
- `WreckCollisionChecks.cs`, `ReferenceShipCollision.cs`: 수정 전 충돌 알고리즘을 테스트 전용 기준으로 보존했다. 6함체, 파괴 유형, 0~10,000초 잔해 갱신, 재파괴/수리, 고속 관통, 다중 접촉, 실제 흩어진 조각 충돌, 0/1e12/-1e16 좌표의 위치·속도·충격·피해를 대조한다. 18가지 레이아웃에서 각각 1,000회 충돌체 갱신 중 관리 힙 할당은 0바이트였다.

### 2026-10-12 — 탄체 후보 검사·함대 규모 부하 시험

기준은 `d15d525`. 탄체마다 모든 함선·미사일·프로브·방어드론 모함을 순회하던 부분을 줄였다. 무장/센서/AI/편성 데이터, 60Hz 월드와 240Hz 연속 충돌은 유지한다.

- `SweepIndex`: 이동 AABB를 가장 넓은 축으로 정렬하고 누적 상한으로 먼 후보를 제외한다. 후보 개수 제한이나 좌표 양자화 없이 원래 순서로 정밀 판정을 수행한다. 배열을 재사용한다.

- 함체/실드 반경은 하위 틱마다 읽고, 명중으로 값이 바뀌면 즉시 갱신한다. 삭제된 미사일·프로브의 참조 순서는 보존하되 현재 생존 상태를 확인한다. 표적 지정 근접신관, 부분 수명, 프로브 60Hz 위치 보간을 유지한다.
